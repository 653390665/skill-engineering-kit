# Usage Principles

## Principle 1: Do not skip planning

A new skill should not begin with SKILL.md. It should begin with a Skill Brief and Architecture Decision.

## Principle 2: Testing is not creation

Pressure testing discovers whether an existing skill behaves correctly. It should not silently invent the skill's purpose.

## Principle 3: Writing is not architecture

A documentation pass can improve clarity, but it should not decide the skill split, safety boundary, or test contract.

## Principle 4: Reports drive optimization

Optimization should be based on standard audit and pressure-test results.

## Principle 5: Keep tool responsibilities separate

The hub coordinates; it does not replace the creator, writer, standard, or pressure tester.
